Use this as the single instruction set for implementing AFLEWO's access-tier and QR system. It supersedes any partial description given earlier in pieces - where this document and an earlier message conflict, this document is correct.

## Context

AFLEWO (aflewo.saemstunes.com) is a Next.js + Supabase site for a worship movement running since 2004, with chapters across Kenya, Tanzania, and Rwanda. The live database already has `profiles`, `chapters`, `chapter_events`, `resources`, `auditions`, `attendance`, `registrations`, `donation_ledger`, `system_audit_logs`, `media_items`, `stories`, `stewards`, `partners`, and a `public.alumni` table (a curated notable-alumni showcase, unrelated to what this document calls the Alumni tier). `profiles.role` is a `user_role` enum (`super_admin, chapter_admin, choir_member, band_member, volunteer, applicant`) reflecting a person's *current* status only - there is no year-scoped history anywhere in the schema before this work.

## 1. Access tiers

Five tiers, resolved server-side, never trusted from the client:

- **Anonymous** - no session.
- **Public** - signed in, `profiles.role = 'applicant'`, no service history.
- **Member** - signed in, has a `service_history` row for the current service year (read from `system_settings.current_service_year`).
- **Alumni** - signed in, has at least one `service_history` row but none for the current service year.
- **Chapter Admin** - `profiles.role = 'chapter_admin'`, scoped to their `chapter_id`.
- **Super Admin** - `profiles.role = 'super_admin'`, global scope.

Tier is computed by one function only: `public.resolve_access_tier(uid uuid) returns access_tier`. Every RLS policy and every server route calls this - never re-implement the logic elsewhere.

## 2. Resource visibility & cascade

Any gated resource (`chapter_events`, `resources`, future gated types) carries `visibility_state` (`hidden | announced_not_open | open | closed`) and `min_tier` (`access_tier`). An admin can lower `min_tier` (Admin → Alumni → Member → Public) as a deliberate write at each step - never an automatic timer, never sideways or back up implicitly. A resource can be held at any cascade level indefinitely.

## 3. QR modal states

Four states, resolved server-side before the modal renders - never computed from client-cached tier:

| State | Trigger | UI |
|---|---|---|
| Loading | check in flight | skeleton |
| Access Granted | `state = open` and viewer tier ≥ `min_tier` | live QR + action button |
| Not Yet Live | `state = announced_not_open` and viewer tier ≥ `min_tier` | countdown + waitlist action |
| Access Denied | viewer tier < `min_tier`, or `state = hidden` | witty redirect, never the literal words "access denied" |

## 4. Chat agent conduct

The agent knows the tier system but never says "tier," "access level," or "you don't have permission" to the user. It never confirms or describes a hidden resource to someone below its `min_tier`. When redirecting a denied request, it offers the most relevant thing that *is* visible to that person, in one warm, varied line - never a fixed template (a fixed line becomes fingerprintable and leaks the boundary). When a resource is `announced_not_open`, the agent is explicit about the date and offers the waitlist action, since the resource's existence is already public at that tier.

## 5. QR token design

Tokens are opaque and random - the QR encodes nothing decodable, only a lookup key. Schema: `qr_tokens(token, identity_fp, user_id, resource_type, resource_id, tier_at_issue, single_use, issued_at, expires_at, consumed_at, scan_count, schema_version)`.

- `identity_fp = HMAC-SHA256(SERVER_SECRET, user_id)`, base32, truncated to 16 bytes - stable forever per user, safe to log, collision-safe at any realistic AFLEWO scale (128-bit space).
- `token` is the instance salt - a fresh 22-char base62 random string on every regeneration for the same user/resource. Same `identity_fp`, new `token`/`issued_at` each time.
- Generation and verification run in a Next.js Route Handler on the **Node runtime** (not Edge, not a separate Supabase Edge Function) - one codebase, one `resolve_access_tier()`, no logic drift between two runtimes. The route uses the user's session-scoped (RLS-respecting) Supabase client for every read; RLS is the enforcement backstop even if the route has a bug.
- Non-negotiable before launch, because changing any of these after real tokens exist breaks or invalidates them: `SERVER_SECRET` value, token entropy (22-char base62), `identity_fp` truncation length (16 bytes), and single-use-vs-reusable policy per resource type (stored as a `single_use` boolean per resource, not a code branch).

## 2. Resource visibility & the cascade rule

Every gated resource (a QR-backed link, an unannounced event, a download) carries a `min_tier` and a `state`.

**State machine per resource:**
- `hidden` - only visible at `min_tier` and above; below that, resource does not exist as far as the client/agent is concerned.
- `announced_not_open` - visible at `min_tier` and above with a countdown; not yet actionable.
- `open` - actionable (QR renders, link resolves) at `min_tier` and above.
- `closed` - was open, now archived; still visible to whoever could see it while open, read-only.

**Cascade rule:** an admin can flip a resource's `min_tier` down (Admin-only → Alumni-visible → Member-visible → Public-visible) but never sideways or back up implicitly - de-escalating visibility is a deliberate write, not automatic. This is what lets HQ announce the Oct 2 event to admins first, then alumni, then members, then the public, each as its own explicit action, not a timer.

A resource can be stopped (frozen at its current `min_tier`) at any cascade level by an admin - this is just setting `state = 'hidden'` again or holding `min_tier` where it is. No separate "freeze" flag needed; the existing fields already express it.

## 5. QR hash/salt design - recommendation

**Where it runs:** a Next.js Route Handler on the **Node.js runtime** (not Edge), e.g. `app/api/qr/[resourceId]/route.ts`. Reasoning:

- Node runtime gives you the full `crypto` module for HMAC without polyfills, and keeps the server secret out of any bundle that could theoretically ship to a client-adjacent runtime.
- Since this is a single Next.js app talking to one Supabase project, an Edge Function would just be a second codebase and a second deploy surface duplicating the same tier-resolution logic - the exact drift risk flagged in §1.2. Keep it in one place.
- Postgres RLS is still the enforcement backstop underneath the route - the route calls Supabase using the **user's session-scoped client** (RLS-respecting), not a service-role key, for every read that determines tier and resource state. Service-role access is reserved for the one write (token issuance) that a normal RLS policy can't cleanly express, and even that write is guarded by the route re-checking tier server-side immediately before it, using the same `resolve_tier()` function from §1.2.

This gives you defense in depth: even if the route handler had a bug, RLS refuses the underlying read; even if RLS had a bug, the route's explicit check catches it.

**What actually goes in the QR - recommendation: don't encode data or a decodable hash at all. Encode an opaque, unguessable token, and store everything server-side.**

This is a cleaner shape than composing the "real" data into the QR and hiding it under a hash, for one concrete reason: a hash of real data is still, structurally, that data - if the hashing scheme is ever partially reverse-engineered or the algorithm has to be published for interop, the QR itself becomes a liability. An opaque random token has nothing to extract even in principle; it's a lookup key, not a container.

**Schema:**

```
qr_tokens
  token            text primary key   -- 22-char base62 random, ~131 bits entropy
  identity_fp      text not null      -- HMAC-SHA256(SERVER_SECRET, user_id), base32, stable forever
  user_id          uuid not null references auth.users(id)
  resource_id      uuid not null
  tier_at_issue    tier_enum not null
  issued_at        timestamptz not null default now()
  expires_at       timestamptz not null
  consumed_at      timestamptz         -- null until scanned, if single-use
  scan_count       int not null default 0
```

- **`identity_fp`** is your stable "identity hash." It's `HMAC-SHA256(SERVER_SECRET, user_id)`, truncated to 16 bytes and base32-encoded. It never changes for a given user, is safe to log and join on for analytics without exposing the raw `user_id`, and at 128 bits of output space, collision risk across even tens of millions of users is not a practical concern - you'd need on the order of 2^64 users before collision probability becomes meaningful (birthday bound), which is many orders of magnitude past AFLEWO's total addressable population since 2004.
- **`token`** is the "instance salt" - freshly random every time someone requests a new QR for the same resource. Regenerating a QR for the same user/resource produces a new `token`, new `issued_at`, new `expires_at`, but the same `identity_fp` and `user_id` - exactly the "same identity, new instance" behavior you described, without needing to hand-construct a composite hash where you manually track which byte ranges are allowed to move.
- **On scan:** look up `token`, verify not expired/not already consumed if single-use, log the analytics event (`resource_id`, `identity_fp`, chapter, timestamp), increment `scan_count`, set `consumed_at` if applicable. This is what gives you accurate per-chapter, per-resource interaction counts - the analytics join is on `identity_fp` and `resource_id`, never on raw user identity.

**Why not compose a single cumulative hash by hand:** what you described - a hash where some byte-ranges are identity-stable and others shift per-instance - is a real, workable pattern, but it means the QR payload itself has to be parsed and partially verified client-side or by whatever scans it, which means the composition scheme becomes a de facto public interface the moment it ships. The token-table approach gets you the identical properties (stable identity component, shifting instance component, uniquely identifiable across your full user history back to 2004) while keeping the actual scheme entirely server-side and free to evolve.

## 6. Non-negotiables before launch

These four decisions become effectively permanent once real tokens exist in production, because changing them invalidates or silently breaks every token issued before the change:

1. **`SERVER_SECRET` for the HMAC** - generate once (32+ random bytes), store in a secrets manager, never in source. Rotating it invalidates every `identity_fp`, which breaks analytics continuity - treat rotation as a full migration event (§7), not routine hygiene.
2. **Token entropy/length** - 22-char base62 (~131 bits) is comfortably future-proof; don't shorten it later for cosmetic reasons.
3. **`identity_fp` truncation length** - 16 bytes (128 bits) is the recommendation; if you truncate shorter to save space, do the birthday-bound math against your actual projected user count first, since this is exactly the kind of change that can't be revisited after the fact.
4. **Single-use vs multi-use tokens per resource type** - decide per resource category (e.g., a Register QR is single-use/consumed on scan; a Download QR may be reusable until `expires_at`) and encode that as data (a `single_use boolean` on the resource), not as a code branch, so it's auditable and changeable per-resource without a deploy.

- **Path A - carry `user_id` forward.** If the future system also has access to the same Supabase `auth.users` table (or a migrated copy preserving UUIDs), it can simply recompute `identity_fp` with a new secret and everyone's fingerprint changes together, in one deliberate cutover, with an explicit mapping table (`old_identity_fp → new_identity_fp`) kept for historical analytics continuity.

CREATE OR REPLACE FUNCTION public.resolve_access_tier(uid UUID)
RETURNS access_tier
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_role user_role;
  v_current_year INT;
  v_has_current BOOLEAN;
  v_has_any BOOLEAN;
BEGIN
  IF uid IS NULL THEN
    RETURN 'anonymous';
  END IF;

  SELECT role INTO v_role FROM public.profiles WHERE id = uid;

  IF v_role IS NULL THEN
    RETURN 'anonymous';
  END IF;

  IF v_role = 'super_admin' THEN
    RETURN 'super_admin';
  END IF;

  IF v_role = 'chapter_admin' THEN
    RETURN 'chapter_admin';
  END IF;

  SELECT (value #>> '{}')::INT INTO v_current_year
  FROM public.system_settings WHERE key = 'current_service_year';

  SELECT EXISTS (
    SELECT 1 FROM public.service_history
    WHERE user_id = uid AND year = v_current_year
  ) INTO v_has_current;

  IF v_has_current THEN
    RETURN 'member';
  END IF;

  SELECT EXISTS (
    SELECT 1 FROM public.service_history WHERE user_id = uid
  ) INTO v_has_any;

  IF v_has_any THEN
    RETURN 'alumni';
  END IF;

  RETURN 'public';
END;
$$;
